### 🔴 BUG #2 — `history` recebido pelo listener é IGNORADO pelo Franz
- **Onde:** `whatsapp_listener.py:868-878` → `compat.py:281-352`
- **Sintoma:** O listener carrega o history corretamente (`get_full_context` retorna até 100 msgs com summary) e passa pra `responder_lead(history=...)` (`whatsapp_listener.py:838, 875`). - **Impacto:** Franz fica míope no turno 2+. Só vê o resumo via `memory_facts` (5 campos) e o histórico de até 5 msgs do `history[-5:]` em `prompts.py:463` — mas só se o history chegar vivo até `build_user_prompt`.

### 🔴 BUG #3 — Race condition outbound_queue × response_executor
- **Onde:** dois caminhos enviando pelo mesmo device sem coordenação
- **Sintoma A (cron)**: `cron_endpoints.py:233` enfileira em `outbound_queue` → worker (`outbound_queue.py:210-365`) chama `sender_func` que é `send_text_parts` direto (`cron_endpoints.py:60`) → set cooldown? NÃO: o worker não chama `set_cooldown_fn` do listener.
- **Sintoma B (inbound)**: `response_executor.py:113` chama `ctx.set_cooldown_fn(ctx.lead_key)` ANTES do envio.
- **Sintoma C (lead_lock Redis)**: `responder_lead` (`compat.py:253`) tem lock Redis de 60s. Mas o worker outbound NÃO passa por `responder_lead` — ele chama `iniciar_contato` (`cron_endpoints.py:197`) que **não está wrapped em `_lead_lock_guard`** (ver `compat.py:85-198`).
- **Resultado:** se um inbound estiver em curso (lead respondeu) e um cron disparar uma outbound ao mesmo lead, as duas execuções podem rodar em paralelo. O `wpp_lock_until` Postgres (`whatsapp_listener.py:719-731`) cobre uma fatia, mas só para `listener.py`, não para o `cron`.

### 🔴 BUG #4 — JSON do LLM vaza pro lead (defesa frágil)

O logger marca como BUG (`whatsapp_listener.py:982`) mas ainda tenta enviar.

### 🔴 BUG #6 — Lock Redis é `FAIL-CLOSED` mas bypass existe
